1. SYSTEM OVERVIEW
--------------------------------------------------------------------------------
Realtime web app for post-event reflection activities. Three roles share one
active session through Firebase Firestore realtime listeners (onSnapshot).
Clients never talk to each other directly; all state changes go through
Firestore. Video files are stored on a local VPS media server (not Firebase
Storage) to stay on the free Spark plan.

Roles
  Host (controller)  Phone of facilitator — run session, edit pages, pick
                     answers onto TV/mobile, upload video, search answers
  TV                 Projector / big screen — QR, questions, floating answers,
                     spotlighted answers, video, messages
  Participant        Attendee phone — join via QR/name, submit text answers

Capacity target
  200+ concurrent participants
  Up to 3 TV screens
  Up to 2 host controllers
  Same fixed URLs for every event (no session id in the path)

Non-goals
  No user-facing login UI (Anonymous Auth only, no credentials form)
  No room lock / invite codes — anyone with /join can enter
  No multiple-choice or rating answers — free text only
  No automatic moderation / profanity filter — host picks what goes on screen
  No multi-tenant concurrent events — one active session via fixed pointer


2. FIXED ROUTES
--------------------------------------------------------------------------------
  /host            Host control (prepare + present)
  /host/history    Past sessions + CSV export
  /host/decks/:id  Edit a saved slide deck (premake, offline from any session)
  /tv              TV display
  /join            Enter display name (encoded in QR)
  /participant     Answer questions (after join)
  *                Redirects to /host

All routes are SPA client routes (Firebase Hosting rewrite -> /index.html).

4. DATA MODEL (FIRESTORE)
--------------------------------------------------------------------------------

system/currentSession
  activeSessionId : string | null
  Purpose: fixed-link pointer so /tv /join /participant always know the live
  session without URL params. Host "start new" / draft creation updates this.
  Old sessions remain under sessions/{id} for history.

sessions/{sessionId}
  title            : string (<= 100)
  status           : "idle" | "presenting" | "ended"
  currentPageIndex : number
                     -1 = QR waiting room (before first page)
                      0..n-1 = index into pages ordered by `order`
  createdAt        : timestamp
  endedAt          : timestamp | null

sessions/{sessionId}/participants/{participantId}
  name     : string (1–40)
  joinedAt : timestamp
  participantId = Firebase Auth anonymous uid

sessions/{sessionId}/pages/{pageId}
  order : number
  type  : "question" | "split_question" | "video" | "message"
  title : string
  content : {
    questionText?      : string   // question/split_question/message main text
    promptA?           : string   // split_question only — label for answer box 1
    promptB?           : string   // split_question only — label for answer box 2
    messageText?       : string
    videoUrl?          : string   // public URL from VPS media server
    videoStoragePath?  : string   // relative path under uploads/
  }
  videoState? : {
    playing   : boolean
    startedAt : timestamp | null  // TV seeks from this for sync
  }

decks/{deckId}
  title      : string (<= 100)
  pageCount  : number   // denormalized count, refreshed on any page CRUD
  createdAt  : timestamp
  updatedAt  : timestamp
  Purpose: reusable, premade slide sets independent of any session. Edited at
  /host/decks/:deckId with the same PageEditor/PageForm used for sessions
  (ownerId=deckId, scope="decks").

decks/{deckId}/pages/{pageId}
  Same shape as sessions/{sessionId}/pages/{pageId} above (order/type/title/
  content/videoState).

sessions/{sessionId}/pages/{pageId}/answers/{answerId}
  participantId : string
  name          : string (1–40)
  text          : string (1–600)
                  // question: raw answer (1–280)
                  // split_question: `${textA}\n${textB}` combined, used for
                  // float/search/CSV fallback
  textA?        : string        // split_question only — answer box 1 (1–280)
  textB?        : string        // split_question only — answer box 2 (1–280)
  createdAt     : timestamp
  showOnTV      : boolean   // default false — host toggle
  showOnMobile  : boolean   // default false — host toggle
  answerId = participant uid  => 1 answer per person per question/split_question page


5. FIRESTORE RULES (SUMMARY)
--------------------------------------------------------------------------------
File: firestore.rules

  system/*           read/write open
  decks              read open
                     create/update if title string <=100
                     delete allowed (cascades pages client-side, see deckService)
  decks/pages        read open; create/update if type in enum; delete allowed
  sessions           read open
                     create/update if title string <=100 and status in enum
                     delete denied
  participants       read open; create/update if name 1–40; delete denied
  pages              read open; create/update if type in enum (incl. split_question);
                     delete allowed
  answers            read open
                     create if name 1–40 and text 1–600 (600 covers split_question's
                     combined `textA\ntextB`; single-box answers stay <=280 in app)
                     update if name/text still within limits (host toggles)
                     delete denied

Indexes: firestore.indexes.json currently empty. Both queries that need
ordering — decks list (orderBy updatedAt desc) and pages within a deck/session
(orderBy order asc) — are single-field orderBy on their own collection, which
Firestore indexes automatically; no composite index required.


6. SESSION LIFECYCLE
--------------------------------------------------------------------------------
1. Host opens /host
2. ensureDraftSession():
   - If pointer session exists and status != ended -> reuse
   - Else create idle session (currentPageIndex=-1), set pointer
3. Host edits title + pages (question / split_question / video / message), reorder,
   upload video
4. Host taps "เริ่มงานใหม่" -> status=presenting, currentPageIndex=-1
5. TV shows QR for /join + live participant count
6. Host next/prev changes currentPageIndex; all clients follow via onSnapshot
7. On question / split_question pages:
   - Participants submit one answer (split_question: both boxes in one submit)
   - Host searches/filters and toggles showOnTV / showOnMobile
   - TV floats recent answers; spotlight for showOnTV=true (split_question shows
     both box texts, one per line)
8. Host "จบงาน" -> status=ended, endedAt=now
9. History at /host/history lists sessions; CSV export client-side

6.1 SAVED DECK FLOW (premake ahead of event day, one-button present)
  a. Save a deck
     - From the idle draft (step 3 above), host taps "บันทึกเป็นชุดสไลด์"
     - saveSessionAsDeck(sessionId, title): creates decks/{deckId} first
       (pageCount=0) then copies pages/{sessionId->deckId} via copyPages(),
       then updates pageCount. Deck doc always exists before its pages, so a
       failed copy never leaves orphaned subcollection docs with no parent.
     - The draft session itself is untouched (still idle, still editable /
       startable directly) — saving as a deck does not consume the draft.
  b. Edit a deck any time, independent of any session
     - /host/decks/:deckId (DeckEditPage) reuses PageEditor/PageForm with
       ownerId=deckId, scope="decks" — same CRUD/reorder/video upload as
       session pages.
  c. Present a deck (event day, one button)
     - Host taps "▶ นำเสนอ" on a saved deck (confirm dialog; different wording
       if something is already presenting).
     - presentDeck(deckId): creates a brand-new sessions/{id} (status=
       presenting, fromDeckId=deckId), copies the deck's pages into it via
       copyPages(), then flips system/currentSession.activeSessionId to the
       new session. Fixed links /tv /join /participant pick it up immediately
       via their existing pointer listener — no URL/session id needed.
     - Whatever session the pointer previously pointed to (the idle draft, or
       a session mid-presentation if the host is switching decks) is closed
       out (status=ended, endedAt=now) once the pointer has moved. This keeps
       /host/history free of dead "กำลังเตรียม"/"กำลังดำเนินการ" rows that can
       never be reached again.
     - Saved decks are never mutated by presenting — presenting always copies,
       so the same deck can be presented repeatedly across events.


7. ROLE FUNCTIONAL REQUIREMENTS
--------------------------------------------------------------------------------

7.1 Host /host
  Prepare (idle)
    - Saved decks panel: list saved decks (title, page count, updated date),
      + สร้างชุดใหม่ (blank deck -> /host/decks/:id), ▶ นำเสนอ, ✎ แก้ไข, ลบ
    - Set session title
    - CRUD pages: add/delete/reorder/edit; types question|split_question|video|message
    - split_question: main question text + promptA/promptB labels for the two
      answer boxes
    - Video page: upload .mp4 <= 200MB with progress bar
    - บันทึกเป็นชุดสไลด์ — save current draft's pages as a new reusable deck
    - Start presenting (from the draft directly, or via a saved deck's
      ▶ นำเสนอ — see 6.1)
  Presenting
    - Show current page; prev/next (disabled at ends)
    - Edit pages anytime ("แก้ไขคำถาม") — realtime for others
    - Question / split_question: list answers newest first (limit 200)
      * Search bar filters by name OR answer text incl. textA/textB
        (case-insensitive substring)
      * Empty search state in Thai when no matches
      * split_question answers show both boxes labeled with promptA/promptB
      * Toggle "ขึ้นจอทีวี" / "ขึ้นจอมือถือ" (multi-select allowed)
    - Video: play/pause writes videoState
    - Live participant count
    - End session
  Links to /host/history

7.2 TV /tv
  - Resolve activeSessionId then subscribe session + pages + participants + answers
  - idle / missing -> waiting message
  - currentPageIndex == -1 -> QR (/join) + count
  - question -> large question text + floating answers (cap ~20–25 DOM) +
    spotlight for showOnTV
  - split_question -> same as question, plus small promptA/promptB line under
    the main question; floating/spotlight answers show textA and textB on
    separate lines
  - video -> fullscreen <video> synced via videoState.playing + startedAt seek
  - message -> fullscreen text

7.3 Join /join
  - Name form 1–40 chars
  - ensureAnonymousAuth() then write participants/{uid}
  - Store name + joined flag in localStorage
  - Redirect /participant
  - Requires Anonymous provider ENABLED in Firebase Console

7.4 Participant /participant
  - If not joined locally -> redirect /join
  - Follow currentPageIndex realtime
  - question: answer form (1–280), one shot per page; see floating + showOnMobile
  - split_question: two labeled textareas (promptA/promptB, 1–280 each),
    submitted together as one answer; see floating + showOnMobile
  - video/message: status text only (no local video playback required)

7.5 History /host/history
  - List sessions by date
  - Detail: questions + split_questions (both boxes) + all answers + names
  - Export CSV (client-generated from Firestore reads); split_question rows
    include separate "คำตอบช่องที่ 1" / "คำตอบช่องที่ 2" columns

11. REALTIME / PERFORMANCE NOTES
--------------------------------------------------------------------------------
Typical listeners per client (approx):
  pointer + session + pages + (participants and/or answers)
With 200 participants + 3 TVs + 2 hosts expect hundreds of concurrent
onSnapshot streams — Firestore handles fanout; keep answer queries limited
(orderBy createdAt desc, limit 30 on TV / 200 on host).

Floating answers: queue + DOM cap prevents TV GPU overload.

Region choice: Singapore Firestore is required for acceptable latency from
Malaysia / SEA audiences. US (nam5) caused ~1.3s per read and felt broken.

Hosting CDN already caches near KUL; not the bottleneck.

VPS (this box): 2 vCPU / 8GB — fine for media + light Express; not intended
as the primary realtime bus for 200 users.

14. KNOWN CONSTRAINTS / DECISIONS
--------------------------------------------------------------------------------
- Videos on VPS over HTTP (not HTTPS): browsers may warn on mixed content
  when page is HTTPS. Prefer same-origin proxy or TLS on :8080 for production
  hardening later.
- Open Firestore rules are intentional for event simplicity; validate lengths
  only. Do not store sensitive personal data.
- Named extra Firestore databases require billing; free path was delete+
  recreate (default) in asia-southeast1.
- Answer document id = auth uid enforces one answer per user per question
  without extra queries.
